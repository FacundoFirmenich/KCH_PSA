# Checkpoint material — reconstrucción KCH_PSA — 2026-11-05

## Posición actual

El proyecto está mejor posicionado que al inicio porque ya no depende de la falsa alternativa “continuar R34 o empezar de cero”. La evidencia permite una tercera vía: preservar R33/AIO2 como precedente operativo acotado, retirar R34 de la interposición activa tras autorización exacta y construir `KCH_PSA` como sucesor independiente que integra los avances Jarvis y el ecosistema 2026 mediante adapters nativos.

## Qué cambió

- Se creó y publicó el repositorio independiente `KCH_PSA`.
- Se localizó un mecanismo plausible y multifactorial para la degradación R34.
- Se verificó que el KCH público preservó R21/R33 y no promovió R34.
- Se separaron tres genealogías: kernel KCH, Jarvis y superficies de producto.
- Se actualizó la arquitectura frente a Cline 2, OpenCode 2, OpenClaw 2, Codex App Server, DeepSeek Harness, Qwen Code, LangGraph y VS Code Agents.
- Se fijó una arquitectura de mancomunidad confederada con sidecar Python, núcleo constitucional y adapters nativos.

## Qué significa

Técnicamente, KCH_PSA puede dejar de ser una colección de prompts, plugins o CLIs conectadas y convertirse en un plano de control verificable sobre harnesses modernos embebibles. Metodológicamente, el proyecto evita transferir autoridad desde tests históricos o títulos de chats. Epistemológicamente, conserva la diferencia entre que una capacidad exista, esté empaquetada, sea soportada por un host, tenga permiso, autoridad y se haya ejecutado realmente.
